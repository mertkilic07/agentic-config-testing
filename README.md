## Research question

> To what extent can agentic AI approaches identify important configuration-option
> interactions that are untested or insufficiently tested, and to what extent can they
> automatically generate effective test cases for these interactions?

The agentic part is **not implemented yet**. The current work builds the experimental
infrastructure that the agent will later use and be evaluated with.

## The experiment in one picture

```
models/sqlite-acts.txt  ──ACTS (2-way)──▶  configs/sqlite-pairwise.csv   (6 configurations)
                                                  │
                    for every row: scripts/run_config.py
                                                  ▼
   build testfixture with the row's flags ─▶ check PRAGMA compile_options
   ─▶ run SQLite's own Tcl tests ─▶ coverage of sqlite3.c (gcovr)
                                                  ▼
                       results/acts/<config>/summary.json
                                                  ▼
                 scripts/make_table.py ─▶ results/coverage_table.md
```

## Getting started (Mac, Windows or Linux)

You only need **Docker Desktop** and **git**. Everything else (SQLite source, Tcl, gcovr,
Java, ACTS) is inside the Docker image.

```sh
git clone https://github.com/mertkilic07/agentic-config-testing.git
cd agentic-config-testing
docker build -t ens491-sqlite .
docker run --rm -it -v "$PWD:/work" ens491-sqlite
```

On Windows PowerShell use `-v "${PWD}:/work"`.

Inside the container (you are user `tester`, in `/work`):

```sh
# 1. (optional) regenerate the covering array with ACTS
bash scripts/generate_acts.sh

# 2. smoke test: one configuration, SQLite's test/main.test (about 30 seconds)
python3 scripts/run_config.py --row 1 --scope main

# 3. real run: one configuration with SQLite's quick test suite
python3 scripts/run_config.py --row 1 --scope quick

# 4. all six configurations (takes hours; good to start in the evening)
python3 scripts/run_config.py --all --scope quick

# 5. results table
python3 scripts/make_table.py --scope quick > results/coverage_table.md
```

Builds and test runs happen in `/home/tester/ens491-work` inside the container, **not** in
the mounted repository. Only the result files are written back to `results/`.

## What `run_config.py` does for one configuration

1. Reads one row of `configs/sqlite-pairwise.csv` (ACTS comment lines are skipped).
2. Turns each value into compiler flags using `models/sqlite-build-mapping.json`.
3. Builds `testfixture` in a fresh directory with
   `CFLAGS="-O0 -g --coverage -fprofile-update=atomic"`.
4. Asks the built `testfixture` for `PRAGMA compile_options` and checks that every option is
   on/off as requested. If not, the run stops and the mismatch is recorded.
5. Deletes the coverage counters written by that check.
6. Runs `test/<scope>.test` from a fresh directory on the container's own filesystem.
7. Measures line and function coverage of `sqlite3.c` only (same boundary for every row).
8. Writes `results/acts/<config>-<scope>/summary.json` with **separate** statuses for build,
   option check, tests and coverage.

## Project roadmap

The project follows the research question in four phases. Each phase builds on the previous one.

| Phase | Question | Main outputs | Status |
|---|---|---|---|
| **1. Experimental infrastructure** | Can we build any configuration of the system, run its own tests and measure coverage, automatically? | Docker environment, configuration model, ACTS covering array, per-configuration runner, results table, option screening | Mostly done: runner works, two silent constraints found, full table in progress |
| **2. Test-gap analysis** | Which option interactions do the existing tests exercise, and which not? | Test-to-option map (`ifcapable`), interaction coverage per test, list of untested pairs | Starting |
| **3. Agentic pipeline** | Can an LLM agent find important untested interactions and write tests for them? | Agent that reads source, docs and tests; generated tests | Not started |
| **4. Evaluation** | Do the agent's findings and tests hold up? | Precision/recall of found gaps, validity of generated tests, coverage before/after | Not started |

Who works on what right now: [docs/team-tasks.md](docs/team-tasks.md).

## Known open issues

- **Baseline failures:** a team member's quick-suite run on the default build reported
  4 errors out of 591,311 tests (`recoverfault-*` allocation-failure tests in
  `ext/recover/recoverfault.test`). Their cause is not established yet; they are not claimed
  to be configuration-interaction bugs.
- **Quick-suite coverage:** an earlier attempt failed in gcovr with negative and suspiciously
  large counters. The runner now builds with `-fprofile-update=atomic` (thread-safe coverage
  counters, `testfixture` uses threads). Whether this fully fixes the problem is being checked.
- **Passed / skipped counts:** SQLite's harness prints "N errors out of M tests"; passed and
  skipped counts are not extracted yet, so they are not reported.
- **Architecture:** the image is built for the host's architecture (ARM64 on Apple Silicon,
  AMD64 on most Windows PCs). Results from different architectures should not be mixed in one
  comparison.
